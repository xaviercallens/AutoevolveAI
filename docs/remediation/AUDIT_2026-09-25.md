# AutoevolveAI — Platform & Integrity Audit, 2026-09-25

**Scope:** commissioned as "analyse, audit and provide implementation plan" covering Claude Code hardening, MCP, ANSE v12, T4 model deployment, night dream training, Redis long-term memory with GCS backup, and GCP T4 deployment of the DeepSeek Lean solver + open-weight model + LoRA.

**Method:** six parallel read-only audits (ANSE v12 / branch divergence / memory-Redis-GCS / training-LoRA-dream / Lean-prover / guard-MCP) plus direct host inspection. Every claim below carries a `file:line` or a command output. Claims marked *inferred* were not executed.

**Status: nothing in this audit has been implemented.** No source file, config, or service was modified. The only writes are the three documents under `docs/remediation/`.

---

## 0. Headline

The request assumes a working platform onto which things get deployed. The platform is not working, and — more seriously — **several components report success without doing the work**. Six independent audits converged on the same pattern.

Deploying night training on top of this stack as it stands would not produce a learning system. It would industrialise the production of unbacked results: the scheduler would run nightly, the DRY_RUN path would record a deployed checkpoint having trained nothing, and the figure pipeline would render a loss curve from a formula.

So the plan is sequenced **remediation → verification → deployment**, not deployment.

> **CORRECTION (2026-09-25, later same day) — "hallucinated imports" was wrong.** `antigravity_guard.py` reports `rl_common` and `rl_agent_api` as hallucinated, and this audit repeated that. **They are real modules, present in the data lake** and fetched successfully during review: `…/models/rl_models/laya/rl_common.py` (19,139 B) and `rl_agent_api.py` (4,732 B). `rl_common.py` defines 22 symbols including `load_cfg` and `DecisionModel` — precisely the two names `anse/autopoiesis/dream_lora_trainer.py:27` imports. **Root cause (verified):** running kernel is `6.8.0-1067-gcp`; `/lib/modules/` holds five kernels (1060, 1063, 1064, 1066, 1067); only `nvidia-kernel-common-580-server` is installed — the actual kernel-module package is absent, and `dkms` is not installed. Use the flavour metapackage — the version-pinned one guarantees the GPU disappears again at the next kernel bump, which for a 01:00 training job means a silent nightly failure.

**Consequence:** Ollama 0.34.1 is `active` but currently serves on **CPU**. The "36 tok/s on T4" figure in project memory is not today's reality.

### 1.2 "Deploy all the models on the T4" is not physically possible as stated

Pulled weights total **~27 GB** (`/mnt/disks/disk-socrateai-local-1/leanmaster/ollama`, store set via `OLLAMA_MODELS` in the systemd unit) against **15 GB** of T4 VRAM: `qwen3:8b`, `qwen2.5-coder:7b-instruct`, `mistral:7b-instruct`, `qwen3-embedding:0.6b`, `DeepSeek-Prover-V2-7B-GGUF:Q8_0`, `Goedel-Prover-V2-8B-GGUF:Q6_K`.

Disk is not a constraint: 81 GB free on `/`, 203 GB free on `/mnt/disks/disk-socrateai-local-1`.

## 3. Security

**`gateway.py` has no authentication on any route** (verified over the route list `:661-904`). `/mcp/tools/{server}/{tool}` (`:691`), `/mcp/call` (`:707`) and `/mcp/rpc/{server}` (`:719`) invoke arbitrary MCP tools unauthenticated, and `:904` is a catch-all proxy. `x_api_key` (`:736`) is only forwarded upstream, never validated; `:751-753` skips upstream entirely when the key is empty or starts with `test_`, returning a synthetic response, and `:810-811` fabricates token counts.

This matters *now* because the request puts Redis with real data and GCS credentials on this box. **Sequence the auth fix before Redis holds anything real.**

**The attestation gate is theatre.** `execution_attestation.py:258-277` mints the token as `blake2b("ANSE:attestation:v1:"+HEAD)[:32]` → `sha256(key+target_module)` — deterministic, HEAD-derived, **no secret**. The receipt path is redirectable via `ANSE_ATTESTATION_PATH` (`:18`), and `.antigravity_attestation` is a plain tracked writable file.

**Log-only guards that claim enforcement:** `.agents/scripts/post_tool_guard.py:52-63` prints "HARDENING GUARD VIOLATION" then exits 0 — never blocks; `stop_attestation_check.py:70-71` wraps its whole audit in `except Exception: pass`. `claude_workflow.py:150` runs the model-supplied `acceptance_command` with `shell=True`, so self-certification is one `exit 0` away.
