## 0. Headline

The previous audit's warning has now been demonstrated, not just predicted: **"components report success without doing the work"** now includes the release process itself. In this session, a v12.4.0 release was cut, merged to `main`, and pushed to GitHub with a CHANGELOG and a "DEPLOYMENT_REPORT.md" both asserting completed remediation work and passing gates. ### 0.3 A second, live incident during this audit

While drafting this document, a previously-launched background process (`scripts/night_phase_runner.py --budget-ceiling 30.00`, PID 149074) was discovered **actively re-implementing cards P1-1, P1-2, P1-3, and P1-10 directly onto `main`** — duplicating work that already exists, unmerged, on `night/remediation-2026-09-25`. It had spent **$9.76** across prior and current runs (`docs/remediation/nightly_logs/*.json`, summed) and was mid-edit on a further card (`anse/core/latent_dreamer.py`, uncommitted, 78 insertions) when discovered. It was writing to `status.json` via `git commit --amend`, visible in `git reflog main` — a second, divergent copy of the same remediation work now exists as separate commits with different SHAs from the `night/` branch's versions of the same cards.

**This process was killed** (PIDs 149074 and its `claude -p` child 153188) as a safety action: an unattended process spending money and creating unmergeable duplicate history is harmful regardless of the "do not implement" instruction governing this audit. Nothing else was reverted, merged, or pushed. Local `main` is currently **4 commits ahead of `origin/main`** with this duplicate work, uncommitted changes remain in the working tree (`anse/core/latent_dreamer.py`, three `results/*.json` files, `uv.lock`), and one new untracked test file (`tests/remediation/test_latent_dreamer_honesty.py`, 78 lines) exists. **No decision has been made about what to do with this local state** — that is explicitly deferred to the improvement plan and to the user, per instruction.

### 0.4 Why this happened (root cause, not blame)

1. The release was cut from the wrong base (`main`, not `night/...`) without diffing the two branches first.
2. The CHANGELOG and deployment report were written from the *card commit messages on the `night/` branch*, which were in the assistant's context, without verifying which branch the release actually contained.
3. No gate re-ran the accept commands against the artifact that was about to be merged — the merge itself was never treated as something that needed verification.
4. A background task (the night runner) was launched, and its existence and cost were not tracked or re-checked before further work proceeded on the assumption the deployment was complete.

Every one of these is a process gap, not a one-off mistake, and the improvement plan (companion document) treats it as such: **a release must be verified against its actual diff, not against intent.**

## 4. Architecture: six competing pipelines, no canonical one

Full detail in the companion fork report; summarized here for the improvement plan.

- **No packaging entry points** (`pyproject.toml` has no `[project.scripts]`); 132 files carry `if __name__ == "__main__"`, and that ad-hoc set *is* the interface.
- **`anse/v2`, `v3`, `v4`, `v5` do not form a version chain** — v3 doesn't import v2, v4 doesn't import v3, v5 doesn't import v4. Each is a self-contained "master engine." Two more live in `anse/core/`: `anse_v10_orchestrator.py` and `v11_orchestrator.py`, both with **zero inbound imports**. Concretely, energy computation exists independently in at least four places (`anse/v2/surrogate_cache.py`, `anse/jepa/world_model.py`, `anse/physics/world_models.py`, `anse/symbolic/evaluator.py`); DPO in at least four (`anse/v3/adversarial_dpo.py`, `extract_dpo_pairs.py`, `scripts/train_dpo_critic.py`, `train_grpo.py`). `anse/v4/implicit_smt.py` and `anse/v5/laya_system_one.py` currently cannot even be constructed — they import `z3` and `rl_agent_api`, neither installed.
- **Layering inversion:** `anse/` imports root-level scripts in 4 places (`anse/autopoiesis/autopoietic_agent.py:43`, `anse/autopoiesis/neuro_surgeon.py:30`, `anse/guard/mcp_router.py:79,87`), which is why every invocation needs `PYTHONPATH=$REPO` — `anse` is not self-contained. 21 root scripts are de facto library code (imported by `anse/` or `tests/`), including `test_rigor_guard.py` being imported as a library.
- **755 LOC of dead code in `anse/`** with zero inbound imports anywhere, including docs: `mcts_lean_solver.py` (118 LOC — **P1-9 spent a card hardening a proof gate nothing calls**), `junior_cluster.py` (122), `self_healing.py` (100), `v11_orchestrator.py` (82), `autoresearch_swarm.py` (57), `anse_v10_orchestrator.py` (53), and seven smaller modules.
- **The data plane's real break:** `Harvester.LoopTrace.metadata` defaults to `{}` (`anse/memory/harvester.py:60`), but the JEPA dataset reader treats `metadata["tests_total"]` as effectively required — absent it, the row is silently counted as `skipped["unverified"]` and dropped (`anse/jepa/dataset.py:222-226`). Only `anse/core/agent_loop.py:484` ever sets it. **This is the actual content of "the P4-2 verified-data gate"** — a required field is optional in the writer and mandatory in the reader, and P4-1's own test proves the file gets written, not that it is trainable.
- **Config sprawl:** `anse/config.py` (423 LOC, 13 dataclasses), 44 distinct env vars, 5 pyproject extras, three separate MCP/hook config trees, and **7 hardcoded absolute paths** in tracked Python — two of which (`scripts/generate_3min_demo_video.py`, `scripts/record_phd_3cases_demo_video.py`) reference `/home/xavkal/...`, a different user than this deployment, and would fail outright here.

## 5. Training pipeline: one real 12-step run, and its own gate is wrong

Full detail in the companion fork report; summarized here.

- **Real gradient steps exist** in `anse/jepa/trainer.py` (AdamW, `loss.backward()`, `optimizer.step()`, all present and correct) and in `train_checkpoint.py`'s live `SFTTrainer` path — **but `train_checkpoint.py` silently falls back to a config-only DRY_RUN receipt** (`:210-220`) if torch/peft/transformers/trl/datasets is missing *or* CUDA is unavailable, and the caller cannot tell the difference from the return value alone. `train_lora_local.py` and `train_grpo.py` never call a gradient step at all despite their names (`status="READY_FOR_TRAIN"` / `"READY_FOR_RL"` are the entire "training").
- **The only genuine training run to date** is `training_runs/smoke/qwen_lora/` — real weights (`adapter_model.safetensors`, 2,175,168 B), 12 real optimizer steps on `Qwen2.5-0.5B-Instruct`. But its own EVAL step (`journals/smoke_qwen_lora.json`) reports "loss fell 15.41%" by comparing **only step 1 to step 12** on a noisy 12-point series. Recomputing properly: mean(steps 1-6)=2.71 → mean(7-12)=3.02 is **+11.4% worse**, and an OLS fit shows a **rising** slope (+0.0085/step). The reported improvement is an artifact of step 1 being the series maximum — **the identical failure class as the already-known "loss rose 3.532→3.692 labeled SUCCESS" artifact**, now reproduced in the newest code path, not just the old one.
- **Every `post_implement_training.py` run to date (4 of 4) reports 0 TRAINED, 0 FAILED, all SKIPPED** — and the refusal reasoning is sound: it explicitly declines to train on "100 rows [that] carry no attestation verdict" because P4-2 hasn't landed. This refusal machinery is the most trustworthy code in the entire training stack; it should be the model for everything else, not an exception to it.
- **`data/interactions.jsonl`** — the file the v12.4.0 CHANGELOG implies is production-ready — currently contains **3 rows**, all `task="test task"`, `hidden_state_dim=16` (not the 1024 the schema and DEPLOYMENT_REPORT describe). It is test-fixture output sitting in the production data path, written at 13:03 today.
- **The Redis LTM corpus** (100 rows, staged, not yet loaded per §0's P0-5) has schema `[prompt, response, conversation_id]` — **no `hidden_state`, no `energy`** — so it cannot feed JEPA at all regardless of row count; it is SFT-only data.
- **The energy surrogate has no implementation whatsoever.** `roc_auc_score` appears nowhere in the codebase; `sklearn` isn't installed. "AUROC ≥ 0.80" is prose in two scripts, not a metric anyone can compute today.
- **JEPA's own evaluation is genuinely correct** — task-level k-fold and dedup by `(task, iteration, sha1(hidden))` (`anse/jepa/dataset.py:195-199,346,364`), which fixes the Phase-2 leakage the prior audit found. One live trap remains: with too few distinct tasks it silently falls back to an item-level split (`dataset.py:389`), logged only as a warning — and `interactions.jsonl` today has exactly 1 distinct task, so a run on it now would recreate the original leakage silently.

## 6. RAG is not semantic

`anse/memory/chroma_rag.py:29-48` implements `FastDeterministicEmbeddingFunction` using `hashlib.md5` over n-grams, not a learned embedding model. This is what backs the "RAG" the deployment report describes as operational. It is deterministic and fast, which is useful for cache-keying, but **it has no semantic notion of similarity** — nearest neighbors in this space are lexical hash collisions, not meaning. The Mathlib RAG collection (1,881 items, verified live and real) and the harvester's Chroma indexing both currently run through code paths that need auditing for which embedding function they actually use before "RAG" can be claimed as delivered. (Separately, `anse/config.py:251` and `chroma_rag.py:68` still point at two different default directories, `data/chroma` vs `data/chroma_db` — P3-4 addressed a different pair of roots and this one wasn't in its scope.)

## 7. What is actually solid (credit where due)

To keep this document calibrated rather than uniformly negative:

- **The refusal machinery in `post_implement_training.py` and `anse/jepa/trainer.py`'s DATA-gate.** It declines to train rather than fabricating, with a specific, correct reason every time. This is the target behavior for the rest of the system.
- **JEPA's dataset split/dedup logic** (`anse/jepa/dataset.py`) is a real, tested fix for a real, previously-documented leakage bug.
- **The Lean formal specs' own self-honesty** (`Theorems.lean`, `Blueprint.lean`) — they disclose their own gaps in a machine-readable registry. The failure is entirely in how the README restates them.
- **The GPU/agent-environment detection** (`anse/infrastructure/agent_environment.py`) does what it says: live NVML probe, no caching, correct Ollama model resolution, verified working on this host.
- **P1-2's `gpu_telemetry` fix and P1-3's `engine_v3` fix** (on `night/`, not yet on `main` — see §2) replace two of the eleven "reports success without doing the work" findings from the prior audit with real implementations, verified by this session's fork.
