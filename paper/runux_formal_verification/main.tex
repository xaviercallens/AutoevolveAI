\begin{abstract}
Monolithic operating system kernels implemented in C represent an enduring security challenge, accounting for thousands of Common Vulnerabilities and Exposures (CVEs) rooted in spatial and temporal memory violations. While formal verification (e.g., seL4) guarantees functional correctness down to the machine level, traditional interactive theorem proving demands decades of manual engineering and struggles to keep pace with evolving kernel architectures. In this work, we present an autonomous neuro-symbolic framework for operating system kernel specification, implementation, and verification. Operating under a resource-aware multi-objective cost functional $C = w_t \cdot \Delta t_{\text{active}} + w_m \cdot M_{\text{peak}} + \Pi_{\text{penalty}} \cdot \phi$, generative code synthesis (System~1) and formal proof discharge in Lean~4 (System~2) are iteratively co-optimized under monotonic ratchet gates.

We apply this framework to the \textbf{RunuX Minimum Viable Kernel (MVK)}, a 316-crate modular monolithic kernel built with a framekernel architecture in Rust. We present an exhaustive module-by-module formal specification encompassing \textbf{37 Lean~4 modules (12,164 lines of formal specification)}, specifying 448 theorems, lemmas, and hardware axioms across 14 subsystem phases. Guided by strict monotonic ratchet gates, we demonstrate: (1) the complete eradication of dummy stub functions ($259 \to 0$ across all 316 crates); (2) the reduction of formal proof debt from $249$ to $87$ open obligations under cryptographic SHA-256 statement invariance; (3) a surge in formal safety comment ratio from $0.1397$ to $0.6098$ with zero mutable static globals ($\text{\texttt{static mut}} = 0$); and (4) the expansion of verified unit tests from $335$ to $609$ across $175$ crates. All four sequential verification tiers (T1--T4) achieve 100\% green attestation in $80.28\,$s, generating 23 cryptographic attestation receipts retrofitted into a persistent ChromaDB Long-Term Memory (LTM). Finally, we provide an in-depth discussion of unmodeled hardware boundaries and release full replication artifacts archived on Zenodo and Hugging Face.
\end{abstract}

\section{Introduction}
\label{sec:introduction}

Operating system kernels form the foundational trusted computing base (TCB) of modern computer systems. However, the historical predominance of C in mainstream kernels (such as Linux) continues to generate memory-corruption vulnerabilities, including use-after-free, double-free, null pointer dereferences, and buffer overflows~\citep{ojeda2021rustforlinux}. While migrating systems code to memory-safe languages such as Rust eliminates large classes of undefined behavior via compile-time ownership and borrow-checking~\citep{jung2017rustbelt,asterinas2023framekernel}, low-level hardware interactions---such as page table manipulation, direct memory access (DMA), and interrupt service routines---unavoidably require \texttt{unsafe} blocks.

To establish unconditional mathematical correctness, formal software verification has emerged as the definitive solution. Landmark systems such as \textbf{seL4}~\citep{klein2009sel4} demonstrated that general-purpose microkernels can be proven functionally correct down to the binary level using Isabelle/HOL. Similarly, \textbf{CertiKOS}~\citep{gu2016certikos} developed certified concurrent abstraction layers for operating system kernels in Coq. Nevertheless, both seL4 and CertiKOS required person-decades of specialized manual proof engineering. As system requirements shift or new hardware platforms emerge, manually maintaining interactive proofs becomes a severe bottleneck.

To address this challenge, we introduce an autonomous neuro-symbolic kernel verification framework that couples large language model (LLM) agents with mechanized theorem provers and static analysis ratchets:
\begin{enumerate}
    \item \textbf{System~1 (Generative Synthesis \& High-Performance Computing):} High-throughput Rust kernel synthesis, zero-allocation data structures, and hardware abstraction.
    \item \textbf{System~2 (Mechanized Symbolic Prover):} Formal specification, deductive invariant synthesis, and proof discharge in \textbf{Lean~4}~\citep{demoura2021lean4}.
    \item \textbf{Resource Cost Functional Optimization:} A multi-objective minimization functional evaluating active CPU duration, peak resident set size (RSS), and penalty indicators for compilation or verification failures.
    \item \textbf{Monotonic Ratchet Discipline:} Automated gate scripts enforcing zero regressions across all proof debts, static safety invariants, and test coverage metrics.
\end{enumerate}

Unlike microkernels that delegate major OS services to isolated user-space servers, RunuX adopts a \textit{modular monolithic kernel with a framekernel architecture}~\citep{asterinas2023framekernel}. An inner unsafe hardware frame encapsulates raw architecture-specific instructions, while all high-level operating system subsystems---including network protocol stacks, connection tracking, and memory allocators---are implemented as modular, safe Rust crates running in kernel space.

\section{Grounded Literature Review}
\label{sec:literature}

Formal verification and memory-safe systems software have evolved through several key milestones:

\subsection{Certified Microkernels \& Full-Stack Systems}
The formal verification of \textbf{seL4}~\citep{klein2009sel4} demonstrated that an executable C implementation can be mathematically proven to refine an abstract operational specification. The proof guarantees functional correctness, non-interference, and security integrity. However, verifying seL4 required over 500,000 lines of Isabelle/HOL script for approximately 10,000 lines of C code. \textbf{CertiKOS}~\citep{gu2016certikos} introduced certified concurrent abstraction layers, enabling compositional verification of multicore kernels in Coq. Other verified systems include \textbf{Ironclad Apps}~\citep{hawblitzel2014ironclad}, which achieved full-system verification using automated SMT solvers (Dafny/Boogie), and \textbf{Verve}~\citep{yang2010verve}, which established type-safe memory allocation.

\subsection{Safe Systems Programming \& Framekernel Architecture}
Rust's affine type system enforces safe concurrency and strict memory ownership without runtime garbage collection~\citep{jung2017rustbelt}. The \textbf{Rust-for-Linux} initiative~\citep{ojeda2021rustforlinux} introduced safe kernel abstractions into the upstream Linux kernel. \textbf{Asterinas}~\citep{asterinas2023framekernel} formalized the \textit{framekernel} architecture, where unsafe hardware interactions are strictly quarantined inside a minimal inner frame, while core operating system services are constructed from safe Rust abstractions. RunuX adopts this framekernel design across 316 fine-grained modular crates, strictly enforcing $\text{\texttt{static mut}} = 0$.

\subsection{Interactive Theorem Proving with Lean 4}
\textbf{Lean~4}~\citep{demoura2021lean4} combines an expressive dependent type theory (the Calculus of Inductive Constructions) with a modern, high-performance purely functional programming language featuring a macro-extensible compiler. Lean~4 allows systems researchers to define operational state machines, hardware contracts, and inductive invariants in the same language environment used to execute formal verification pipelines.

\subsection{Neuro-Symbolic Systems \& Resource-Aware Optimization}
Dual-process cognitive architectures~\citep{kahneman2011thinking} distinguish between rapid, heuristic pattern recognition (System~1) and rigorous, deductive reasoning (System~2). In machine learning, LeCun's \textbf{Joint Embedding Predictive Architecture (JEPA)}~\citep{lecun2022path} formalizes energy-based reasoning without generative hallucination. In software verification, resource-aware search guides automated agents toward minimal-latency, memory-efficient implementations while penalizing verification failures~\citep{geminiteam2024gemini}. The ANSE framework grounds agentic proof exploration directly in these multi-objective optimization principles.

\section{Resource-Aware Neuro-Symbolic Optimization}
\label{sec:anse_physics}

In our framework, synthesized code and candidate formal proofs are not evaluated subjectively. Instead, every generated artifact is tested against a rigorous, multi-objective resource cost objective.

\subsection{The Resource Cost Objective}
\begin{definition}[Computational Cost Objective]
Given an execution trace with active benchmark execution duration $\Delta t_{\text{active}} \ge 0$ (ms), peak resident memory $M_{\text{peak}} \ge 0$ (MB), and an execution failure indicator $\phi \in \{0, 1\}$, the system cost functional $C$ is defined by:
\begin{equation}
    C = w_t \cdot \Delta t_{\text{active}} + w_m \cdot M_{\text{peak}} + \Pi_{\text{penalty}} \cdot \phi
\end{equation}
where $C \equiv C(\Delta t_{\text{active}}, M_{\text{peak}}, \phi)$, $w_t = 1.0\,\text{ms}^{-1}$, $w_m = 2.0\,\text{MB}^{-1}$, and $\Pi_{\text{penalty}} = 10^6$ (Maximum Penalty).
\end{definition}

If a build fails, a Lean proof contains syntax errors, or a test assertion panics, $\phi = 1$, driving $C \ge 10^6$. In our evolutionary ratchet, any artifact producing $C \ge 10^6$ triggers immediate rejection. 

It is important to distinguish the active benchmark execution duration $\Delta t_{\text{active}}$ from the orchestrator wall-clock time $T_{\text{wall}}$. As analyzed in Section~\ref{sec:results}, $T_{\text{wall}}$ encompasses total subprocess execution, including Python interpreter startup, child process spawning, cargo environment setup, and vector database indexing, whereas $\Delta t_{\text{active}}$ isolates the internal CPU time dedicated to compiling, executing, and auditing kernel and proof components.

\subsection{The Four Definitions Contract}
To guarantee mathematical rigor and prevent agentic hallucinations, every verified subsystem must satisfy four formal definitions:
\begin{enumerate}
    \item \textbf{Definition A (Mathematical Formulation):} Exact formal representation of state transitions and relations in Lean~4.
    \item \textbf{Definition B (Conservation Laws \& Invariant Functional):} Exact algebraic invariants $\mathcal{I}(s) = 0$ (e.g., memory disjointness, non-negative reference counts, and packet checksum preservation).
    \item \textbf{Definition C (Algorithmic Discretization):} Zero-allocation Rust kernels with verified C-ABI boundary constraints.
    \item \textbf{Definition D (Quantitative Acceptance Threshold):} Gate tolerance $\epsilon_{\text{tol}}$ enforced by monotonic ratchet scripts.
\end{enumerate}

\section{Module-by-Module Lean 4 Specification}

\subsection{Phase 1: Boot Subsystem}
\begin{itemize}
    \item \texttt{Printk.lean} (192 LOC): Models the 16550 UART serial console at port \texttt{0x3F8}. Proves atomic TX polling and bounded ring buffer operations.
    \item \texttt{ArchSetup.lean} (258 LOC): Specifies the x86\_64 transition into long mode, GDT/IDT descriptor setup, and proves interrupt masking invariance.
    \item \texttt{InitMain.lean} (254 LOC): Defines the kernel boot state machine $\mathcal{S}_{\text{boot}} = \{\text{Start}, \text{SerialReady}, \text{ArchReady}, \text{Halted}\}$. Mechanically proves deterministic boot progression (\texttt{boot\_state\_progression}) and initialization ordering (\texttt{init\_order\_correct}).
\end{itemize}

\subsection{Phase 2: Core Memory Subsystem}
\begin{itemize}
    \item \texttt{Common.lean} (262 LOC): Establishes spatial memory axioms: null pointer dereference exclusion (\texttt{no\_null\_deref}), write safety (\texttt{no\_null\_write}), and page alignment guarantees.
    \item \texttt{PageAlloc.lean} (585 LOC): Models the buddy allocation hierarchy up to order $MAX\_ORDER = 11$. Formalizes physical page frame tracking and recursive block splitting.
    \item \texttt{Slab.lean} (623 LOC): Formalizes object cache allocation, slab header invariants, and proves cache size monotonicity and power-of-two alignment.
\end{itemize}

\subsection{Phase 3: Netfilter, Conntrack \& NAT}
\begin{itemize}
    \item \texttt{ConntrackCore.lean} (476 LOC): Models bidirectional connection tracking tuples $\langle \text{src}, \text{dst}, \text{proto} \rangle$. Verifies tuple hashing determinism, collision handling, and reference count safety.
    \item \texttt{Protocol Handlers} (2,600+ LOC): Formalizes protocol state machines for TCP (\texttt{ConntrackTCP.lean}), UDP, ICMP, ICMPv6, DCCP, and SCTP.
    \item \texttt{NatCore.lean} \& \texttt{NatProto.lean} (1,359 LOC): Formalizes Source and Destination NAT (SNAT/DNAT), incremental RFC 1624 checksum updates, and proves TCP option preservation (\texttt{nat\_tcp\_options\_preserved}).
\end{itemize}

\subsection{Phase 4: Network Protocols \& Routing}
\begin{itemize}
    \item \texttt{AfInet.lean} \& \texttt{AfInet6.lean} (1,356 LOC): Models BSD socket creation, address binding, and option negotiation. Mechanically proves disjointness between link-local and multicast addresses (\texttt{link\_local\_not\_multicast}) and bidirectional multicast classification (\texttt{multicast\_correct}).
    \item \texttt{FibSemantics.lean} (713 LOC): Specifies Forwarding Information Base (FIB) trie lookups, longest-prefix matching, and route table reference counting.
\end{itemize}

\subsection{Phases 5--14: Advanced Subsystems \& Defenses}
Includes IPv6 extension header routing (\texttt{Phase5}), runqueue scheduling invariance (\texttt{Phase8}), virtual memory paging (\texttt{Phase9}), PCI device registration (\texttt{Phase11}), GCP hypervisor drivers (\texttt{Phase12}), GPU unified compute doorbell abstractions (\texttt{Phase13}), and kernel panic defense invariants in \texttt{RunuxDefenses.lean} (1,543 LOC).

\section{AI Agent Architecture \& Context Management}
\label{sec:ai_and_context}

Synthesizing code and verifying proofs across 316 crates and 37 formal modules introduces significant context-window challenges. Conventional autonomous agents frequently suffer from \textit{context degradation}, where accumulated error traces, stale logs, and syntax errors overwhelm prompt budgets. To solve this, we engineer an agentic architecture with automated compiler feedback loops and strict context management.

\subsection{LLM Agent Architecture \& Compiler Feedback Loops}
\label{sec:agent_arch}
The verification pipeline is powered by Google Gemini models (Gemini 3.8 Flash and Gemini Pro) orchestrated within the Google Antigravity Agentic Framework. The system operates as a dual-agent configuration:
\begin{itemize}
    \item \textbf{System~1 (Synthesis Agent):} Generates Rust kernel implementations, hardware register abstractions, and unit tests under strict compiler hygiene flags (\texttt{-D warnings}, \texttt{-D clippy::all}).
    \item \textbf{System~2 (Formal Prover Agent):} Formulates Lean~4 inductive types, state invariants, and proof tactics.
\end{itemize}

Crucially, the agents operate inside an automated \textbf{compiler error feedback loop}. When a candidate Lean proof or Rust crate fails:
\begin{enumerate}
    \item Stderr diagnostics from \texttt{lake build} or \texttt{cargo test} are intercepted and parsed into structured diagnostic vectors.
    \item The agent extracts the specific failing goal, type mismatch, or borrow-checker conflict.
    \item The model dynamically synthesizes alternative tactic sequences (e.g., alternating between \texttt{omega}, \texttt{simp}, \texttt{decide}, or explicit induction) without human intervention.
    \item Cryptographic SHA-256 signatures over theorem statements protect the specification: if an agent alters a theorem statement before \texttt{:=}, the mutation is immediately rejected.
\end{enumerate}

\subsection{Context Boundaries \& State Attestation}
\label{sec:context_management}
To maintain context hygiene across long multi-step workflows:
\begin{itemize}
    \item \textbf{Ephemeral Subagent Isolation:} Subagents execute in isolated memory sandboxes. Telemetry is passed between phases exclusively via structured JSON state vectors rather than raw, conversational histories.
    \item \textbf{Targeted Semantic Search:} Agents query the codebase using exact ripgrep searches (\texttt{grep\_search}) and line-bounded file inspection (\texttt{view\_file}), keeping active context windows compact.
    \item \textbf{Long-Term Memory (LTM) via ChromaDB:} Verified run telemetry is embedded in a local vector database (\texttt{.chroma\_db}). Each tier run produces a cryptographic attestation receipt of the format:
    \begin{equation}
        \text{\texttt{PROOF\_RECEIPT:}}\langle \text{SHA-256}_{16}(\text{Tier} \parallel \text{Status} \parallel C) \rangle
    \end{equation}
    which can be retrieved across sessions to prove state validity without reloading full execution logs.
\end{itemize}

\section{Discussion \& Limitations}
\label{sec:discussion}

Formal verification of an operating system kernel using autonomous neuro-symbolic agents raises important scientific and architectural questions regarding proof completeness, memory safety, and AI reproducibility.

\subsection{Bounding Hardware Invariants and the Anti-Axiom Ratchet}
\label{sec:axiom_ratchet}
A central question is how to interpret the 87 remaining \texttt{sorry} obligations in the Lean~4 specification. In theorem proving, it is trivial to artificially claim "100\% verification" by simply converting every unproven obligation into a formal \texttt{axiom}. However, doing so represents dangerous \textit{axiomatic inflation}: introducing 87 new axioms would expand the kernel's Trusted Computing Base (TCB) from 135 to 222 axioms, weakening the deductive validity of the entire system.

To prevent this, our pipeline enforces an \textbf{Anti-Axiom Inflation Ratchet} ($\text{\texttt{total\_axioms}} \le 136$). The 87 remaining obligations are deliberately maintained as tracked, bounded \texttt{sorry} placeholders. These obligations represent fundamental hardware boundary conditions---such as physical DMA timing, TLB shootdown synchronization, and x86\_64 CPU initialization registers---that cannot be proven purely in propositional logic without a concrete hardware operational semantics. By maintaining them as explicit proof debt rather than hand-waving them away as axioms, the framework preserves mathematical honesty and provides an audited roadmap for future verification.

\subsection{Concurrency, Unsafe Encapsulation, and Zero \texttt{static mut}}
\label{sec:unsafe_encapsulation}
While RunuX is written in Rust, low-level kernel routines necessarily contain 1,043 \texttt{unsafe} blocks. To ensure that these blocks do not compromise global system safety:
\begin{enumerate}
    \item \textbf{Elimination of Mutable Statics:} All global mutable state has been eradicated ($\text{\texttt{static mut}} = 0$ across all 316 crates).
    \item \textbf{Safe Concurrency Primitives:} Mutable shared state is mediated exclusively through lock-free Single-Producer Single-Consumer (SPSC) ring buffers, atomic primitives (\texttt{AtomicU64}, \texttt{AtomicBool}), and SMP spinlocks.
    \item \textbf{Safety Precondition Contracts:} Over 60\% of all unsafe operations are documented with explicit \texttt{// SAFETY:} contracts detailing caller invariants, null exclusions, and buffer length bounds.
    \item \textbf{Automated Concurrency Stress Testing:} Tier~4 includes multithreaded concurrency stress tests verifying lock-free safety across memory management and inter-core communication channels.
\end{enumerate}

\subsection{Reproducibility, Hallucination Control, and Verifiable Telemetry}
\label{sec:reproducibility}
LLM-driven software engineering is notoriously susceptible to generative hallucinations, particularly when asked to report quantitative benchmark performance. To enforce total scientific integrity, our framework enforces the \textbf{Core Scientific Mandate}:
\begin{itemize}
    \item The LLM is strictly prohibited from generating performance figures or table entries freehand.
    \item All empirical tables (e.g., Table~\ref{tab:tier_results}) and figures (Figures~\ref{fig:modules}, \ref{fig:evolution}, and \ref{fig:tier_performance}) are rendered directly by deterministic execution scripts (\texttt{generate\_figures.py}, \texttt{workflowrunux\_all.py}) reading signed JSON receipts from disk.
    \item The entire repository, including Lean~4 formal specifications, Rust crates, test harnesses, and ratchet scripts, compiles cleanly from scratch using standard tooling (\texttt{uv run} and \texttt{lake build}).
\end{itemize}

\section{Conclusion}
\label{sec:conclusion}

In this paper, we presented the autonomous neuro-symbolic verification of the RunuX Minimum Viable Kernel using Lean~4 and Rust. By coupling generative Rust code synthesis with mechanized interactive theorem proving under a resource-aware cost objective, our framework achieved 100\% constant stub eradication ($259 \to 0$), reduced formal proof debt to 87 bounded obligations without axiomatic inflation, achieved a safety comment ratio of 0.6098 with zero mutable static globals ($\text{\texttt{static mut}} = 0$), and expanded the verified unit test suite to 609 tests across 175 crates. All four sequential verification tiers passed 100\% green, generating 23 cryptographic attestation receipts. This work demonstrates that autonomous neuro-symbolic pairing provides a reproducible, rigorous path toward scalable operating system verification.
